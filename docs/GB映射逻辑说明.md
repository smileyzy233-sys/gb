# GB 标准映射说明：零基础交接版

> **适用对象**：没有参与本项目、不了解标准体系或编程流程的协作者。
> **阅读目标**：看完后能够解释“为什么某条 GB 标准会匹配到某项国际标准”，并能对疑难记录进行人工复核。
> **对应代码**：`src/standard_pipeline/gb_mapping.py`
> **对应数据库**：`GB映射参考数据库/GB_dict.csv`
> **依据版本**：GitHub 仓库 `smileyzy233-sys/gb` 的 `main` 分支，提交 `aba587e`（“gb映射重构”）。

## 1. 先用一句话理解这项工作

企业年报可能只写了一项中国国家标准，例如：

```text
GB/T 17650.2
```

但我们的研究需要判断：

> **企业在该年报年份提到或采用的这个 GB 标准，当时对应哪一项国际标准？**

因此，GB 映射不是“看到 GB 就随便找一个 ISO”，而是下面这条链条：

```text
年报中的 GB 写法
→ 整理成可查询的标准号
→ 判断企业有没有写明 GB 版本年份
→ 若未写明版本年份则根据年报年份找到正确的 GB 历史版本
→ 读取这个 GB 版本同一行对应的国际标准
→ 再结合企业是否实际采用，决定 output 是 1 还是 0
```

最重要的原则是：

> **先确定正确的 GB 版本，再读取该版本对应的国际标准。**

不能直接选择数据库里最新的 GB 版本，也不能脱离 GB 版本，直接选择最新的 ISO 或 IEC 版本。

可以把它想成“查教材版本”：

```text
GB/T 17650.2        = 教材名称
1998 版、2021 版    = 同一本教材的不同版本
2020 年年报          = 我们要还原的历史时间点
```

2020 年的人不可能自动使用 2021 年才生效的版本。因此，看到数据库里有更新版本，并不代表历史年报就应匹配到更新版本。

### 30 秒看懂一个完整例子

```text
年报输入：2020 年年报写“符合 GB/T 17650.2”
企业没有写版本年份
数据库中有 1998 版和 2021 版
2020-12-31 时：1998 版仍有效，2021 版尚未实施
所以选择：GB/T 17650.2-1998
再读取同一行：IEC 60754-2:1991
若 status=ADOPTED，则 output=1
```

整份说明只是把这段判断拆开讲清楚。

## 2. 这一步只处理哪类标准

Stage2 会把标准实体分成不同类型。GB 映射只处理：

```text
TYPE_B：需要通过中国国家标准映射表，转换成国际标准的记录
```

例如：

```text
GB/T 19001-2016
GB 3836.1-2021
GB/T 17650.2
```

下面两类不走 GB 映射：

- `TYPE_A`：年报已经直接写出 ISO、IEC 等国际标准；
- `TYPE_C`：项目中定义的其他国际认证或规则类实体。

所以，人工复核前第一件事是确认：

```text
type 是否等于 TYPE_B？
```

不是 `TYPE_B`，就不需要查 `GB_dict.csv`。

## 3. 一条记录中，哪些信息分别有什么用

假设 Stage2 输出一条记录：

| 字段         | 示例                      | 用途                                             |
| ------------ | ------------------------- | ------------------------------------------------ |
| `entity`   | `GB/T 17650.2`          | 年报中识别出的 GB 标准号                         |
| `year`     | `2020`                  | 这条记录来自哪一年的年报                         |
| `type`     | `TYPE_B`                | 表示需要进行 GB 映射                             |
| `status`   | `ADOPTED`               | 表示企业被判断为实际采用、执行、符合或通过该标准 |
| `evidence` | 公司产品符合 GB/T 17650.2 | 支撑模型判断的年报原文                           |

其中，GB 版本匹配主要使用：

```text
entity + year
```

最终 `output` 还要使用：

```text
status
```

换句话说：

- `entity` 和 `year` 决定“映射到哪个国际标准”；
- `status` 决定“这项映射是否能计为企业实际采用”。

这两个判断不能混在一起。

## 4. 必须分清的三个年份

这是整个映射中最容易混淆的地方。

### 4.1 年报年份

表示这条记录来自哪一年的年报。

例如：

```text
year = 2020
```

项目把该年的最后一天作为历史判断时点：

```text
2020 年年报 → 判断截止日为 2020-12-31
```

### 4.2 GB 版本年份

标准号末尾的年份，表示这项 GB 标准是哪一版。

例如：

```text
GB/T 19001-2016
```

其中：

- 基础编号：`GB/T19001`
- GB 版本年份：`2016`

注意：但有些年报中标准没有末尾年份，此时我们根据年报时间来判断，后续会有示例

### 4.3 国际标准版本年份

GB 映射成功后，可能得到：

```text
ISO 9001:2015
```

这里的 `2015` 是国际标准自己的版本年份。

它不需要与 GB 版本年份或年报年份相同。

例如：

```text
2020 年报
→ GB/T 19001-2016
→ ISO 9001:2015
```

这是正常情况，不是年份错误。

## 5. 什么是“基础编号”

同一项标准可能先后发布多个版本：

```text
GB/T 17650.2-1998
GB/T 17650.2-2021
```

去掉末尾版本年份后，两者都属于同一个基础编号：

```text
GB/T17650.2
```

因此，程序先把标准拆成：

```text
基础编号 + 版本年份
```

示例：

| 原始标准号          | 基础编号        | 版本年份 |
| ------------------- | --------------- | -------: |
| `GB/T 19001-2016` | `GB/T19001`   |     2016 |
| `GB 3836.1-2021`  | `GB3836.1`    |     2021 |
| `GB/T 17650.2`    | `GB/T17650.2` |   未写明 |

基础编号的作用是：

> 把同一项标准的不同历史版本放在一起比较。

## 6. 第一步：先把各种不统一写法整理成统一形式

年报中的标准号格式经常不统一。程序会进行一部分自动规范化，包括：

- 英文字母统一为大写；
- 全角字符转换为半角字符；
- 去除多余空格；
- 将多种横线统一为普通半角横线 `-`；
- 接受冒号 `:` 作为版本年份分隔符；
- 保留小数点，例如 `3836.1`、`17650.2`。

### 6.1 通常可以自动识别为同一标准的写法

下面这些写法会被理解为同一个标准：

| 年报中的写法                      | 程序理解的基础编号 | 版本年份 |
| --------------------------------- | ------------------ | -------: |
| `GB/T 19001-2016`               | `GB/T19001`      |     2016 |
| `gb/t 19001-2016`               | `GB/T19001`      |     2016 |
| `GB/T19001:2016`                | `GB/T19001`      |     2016 |
| `GB / T 19001—2016`            | `GB/T19001`      |     2016 |
| `GB/T 19001－2016`              | `GB/T19001`      |     2016 |
| `ＧＢ／Ｔ １９００１－２０１６` | `GB/T19001`      |     2016 |
| `GB/T 17650.2-1998`             | `GB/T17650.2`    |     1998 |
| `GB 3836.1-2021`                | `GB3836.1`       |     2021 |

### 6.2 两位版本年份的处理

程序也接受两位年份：

```text
GB/T 19001-16 → 2016
GB/T 1234-99 → 1999
```

程序使用的换算规则是：

- `00` 至 `50`：理解为 2000 至 2050；
- `51` 至 `99`：理解为 1951 至 1999。

但两位年份本身容易产生歧义，因此人工复核时最好回到原文确认，不要只依赖自动转换。

### 6.3 不能可靠自动识别、需要人工改正的写法

下面这些写法不要直接交给映射程序猜测：

| 原始写法                             | 问题                                                 | 建议改成                          |
| ------------------------------------ | ---------------------------------------------------- | --------------------------------- |
| `GB/T190012016`                    | 编号与年份完全连在一起，无法判断 2016 是否为版本年份 | 核对原文后改成`GB/T 19001-2016` |
| `GB/T 19001（2016）`               | 当前解析规则不把括号中的年份当作版本年份             | 改成`GB/T 19001-2016`           |
| `GB-T 19001-2016`                  | `GB/T` 被错误写成 `GB-T`，可能形成错误基础编号   | 核对后改成`GB/T 19001-2016`     |
| `GBT 19001-2016`                   | 缺少`/`，不能保证与 `GB/T19001` 匹配             | 核对后补成`GB/T 19001-2016`     |
| `GB/T 19001-2016 质量管理体系要求` | 标准名称混入`entity`，可能导致整串无法匹配         | 只保留`GB/T 19001-2016`         |
| `GB/T 19001-2016（ISO 9001:2015）` | 括号说明混入标准实体                                 | GB 与 ISO 分开记录                |
| `GB/T 19001-2016、GB/T 24001-2016` | 一条`entity` 中包含两个标准                        | 拆成两条记录分别匹配              |

核心要求是：

> `entity` 中最好只保留一个完整标准号，不要带标准名称、括号解释或第二个标准号。

## 7. 第二步：判断标准号有没有写明版本年份

这是整个流程的分叉点。

### 情况 A：写明了版本年份

例如：

```text
GB/T 17650.2-2021
```

处理原则是：

> **只查 2021 版，不允许自动退回 1998 版，也不允许换成其他年份。**

### 情况 B：没有写版本年份

例如：

```text
GB/T 17650.2
```

这时无法直接知道企业指的是哪一版，需要结合年报年份，从该基础编号的所有历史版本中选择当时有效的一版。

两种情况的规则不同，不能混用。

---

## 8. 情况 A：标准号已经写明版本年份，如何匹配

假设年报中写的是：

```text
GB/T 17650.2-2021
```

程序按下面顺序判断。

### A1. 基础编号和版本年份是否都能精确找到

查询条件是：

```text
基础编号 = GB/T17650.2
版本年份 = 2021
```

如果数据库中没有这个精确版本：

```text
匹配失败
```

程序不会因为存在 1998 版，就自动改用 1998 版。

#### 示例：版本不存在

```text
年报输入：GB/T 19001-2020
数据库只有：GB/T 19001-2016、GB/T 19001-2024
```

结果：

```text
没有 2020 版
→ 不回退到 2016 版
→ 也不前进到 2024 版
→ 未找到映射
```

### A2. 版本年份是否晚于年报年份

例如：

```text
2020 年年报写：GB/T 17650.2-2021
```

2021 版晚于 2020 年报，因此拒绝匹配。

```text
2021 > 2020
→ 拒绝
```

### A3. 该版本到年报年末是否已经实施

即使标准号叫“2012 版”，也可能到 2013 年才正式实施。

程序会比较：

```text
生效日期 <= 年报年份的 12 月 31 日？
```

若生效日期更晚，就拒绝。

例如：

```text
年报年份：2012
标准版本：某 GB-2012
实际生效日期：2013-05-01
```

则：

```text
2013-05-01 晚于 2012-12-31
→ 当年年末尚未实施
→ 拒绝匹配
```

### A4. 当前程序对“明确写出的旧版标准”有一个边界

当前代码在企业已经明确写出版本年份时，会检查：

- 精确版本是否存在；
- 版本年份是否晚于年报年份；
- 生效日期是否晚于年报年末。

但是，当前代码**不会继续检查该明确版本在年报年末是否已经失效**。

例如，数据库中：

```text
GB/T 17650.2-1998
失效日期：2021-11-01
```

如果 2022 年年报仍明确写：

```text
GB/T 17650.2-1998
```

当前程序仍可能精确映射到：

```text
IEC 60754-2:1991
```

如果 `status=ADOPTED`，当前程序还可能给出 `output=1`。

人工复核时应：

1. 不要擅自把 1998 版换成 2021 版；
2. 保留企业明确写出的 1998 版；
3. 增加复核备注：

```text
企业明确引用已失效旧版本；当前程序仍可精确映射，需按研究口径决定是否保留。
```

## 9. 情况 B：标准号没有写版本年份，如何匹配

假设记录是：

```text
entity = GB/T 17650.2
year = 2020
```

由于企业没有写明版本，程序需要查看同一基础编号的全部版本。

数据库中假设有：

| GB 版本               | 生效日期   | 失效日期   | 当前状态 | 国际标准             |
| --------------------- | ---------- | ---------- | -------- | -------------------- |
| `GB/T 17650.2-1998` | 1999-10-01 | 2021-11-01 | 废止     | `IEC 60754-2:1991` |
| `GB/T 17650.2-2021` | 2021-11-01 | 空白       | 现行     | `IEC 60754-2:2019` |

2020 年报的判断截止日是：

```text
2020-12-31
```

程序逐个排除不合格版本。

### B1. 排除版本年份晚于年报年份的版本

```text
2021 版 > 2020 年报
→ 排除 2021 版
```

### B2. 排除到年报年末尚未实施的版本

```text
生效日期 > 2020-12-31
→ 排除
```

### B3. 排除在年报年末以前已经失效的版本

程序使用的有效区间可以理解为：

```text
生效日期 <= 年报截止日 < 失效日期
```

注意右边是不包含失效日的。

例如：

```text
失效日期 = 2021-11-01
```

则该版本在 `2021-11-01` 当天及以后不再被视为有效。

### B4. 排除“已废止但没有可靠失效日期”的版本

在记录具有可解析的生效日期时，如果同时出现：

```text
当前状态 = 废止
失效日期 = 空白
```

程序不会用它进行无版本年份的历史推断。

原因是：没有可靠的失效日期，无法证明它在年报年末仍然有效。

需要注意：如果该记录连生效日期也缺失，当前代码可能绕过这项时间检查，具体边界见第 15 节。

### B5. 排除没有历史时间元数据的旧表记录

如果：

```text
时间数据质量包含 LEGACY_ONLY_NO_TEMPORAL_METADATA
```

这类记录不会参与“未写版本年份”的自动选择。

它可能保存了有价值的旧采标信息，但缺少足够的生效和失效时间，不能用于严格的历史版本判断。

### B6. 在剩余版本中选择最接近年报年末的一版

经过排除后，如果还剩多个可用版本，程序选择：

```text
生效日期最晚、且不晚于年报截止日的版本
```

回到示例：

```text
2020 年报：GB/T 17650.2
```

- 1998 版在 2020-12-31 已实施且尚未失效；
- 2021 版在 2020-12-31 尚未实施。

因此：

```text
GB/T 17650.2
→ GB/T 17650.2-1998
→ IEC 60754-2:1991
```

这里绝不能因为数据库中 2021 版更新，就把 2020 年报映射到 2021 版。

## 10. 没有版本年份时，可以用一个简单问题来判断

对每个候选版本依次问：

```text
截至这份年报年份的 12 月 31 日，
这个版本是否已经实施，而且尚未失效？
```

- 回答“是”：保留为候选版本；
- 回答“否”：排除；
- 无法回答：进入人工复核，不要凭感觉选最新版本。

最后，在所有可靠候选中选择当时最新生效的一版。

---

## 11. 第三步：确定 GB 版本后，读取国际标准

找到正确 GB 版本后，只做一件事：

> 查看该 GB 版本所在行的 `国际标准编号`。

例如：

```text
GB/T 17650.2-1998
→ 国际标准编号：IEC 60754-2:1991
```

正确映射链条是：

```text
年报中的 GB/T 17650.2
→ 根据 2020 年报选择 GB/T 17650.2-1998
→ 读取同一行的 IEC 60754-2:1991
```

不能做下面这些事情：

- 不能自行搜索名称相近的 ISO 或 IEC 标准；
- 不能把国际标准替换成最新版本；
- 不能因为国际标准年份较旧就认定映射错误；
- 不能跨到另一个 GB 版本所在行读取国际标准。

如果正确 GB 版本的 `国际标准编号` 为空：

```text
GB 版本匹配成功
≠
国际标准映射成功
```

此时仍然不能形成有效国际标准记录。

---

## 12. 第四步：为什么映射成功后还不一定 output=1

GB 映射解决的是：

```text
这个 GB 版本对应哪项国际标准？
```

`status` 解决的是：

```text
企业是否被判断为实际采用这项标准？
```

只有以下三个条件同时成立，`output` 才是 1：

1. `type=TYPE_B`；
2. 找到符合时间规则的 GB 版本，并且该行国际标准编号非空；
3. `status=ADOPTED`。

判断表如下：

| GB 版本是否找到 | 国际标准编号是否存在 | `status`    | `output` |
| --------------- | -------------------- | ------------- | ---------: |
| 是              | 是                   | `ADOPTED`   |          1 |
| 是              | 是                   | 非`ADOPTED` |          0 |
| 是              | 否                   | `ADOPTED`   |          0 |
| 否              | —                   | `ADOPTED`   |          0 |

因此：

> `output=0` 不一定表示企业肯定没有采用国际标准。

它还可能表示：

- 标准号格式无法解析；
- 精确版本不存在；
- 版本晚于年报年份；
- 到年报年末尚未实施；
- 没有可靠历史版本；
- GB 版本找到了，但国际标准编号为空；
- 企业状态不是 `ADOPTED`。

## 13. 八个完整示例

### 示例 1：未写版本年份，选择年报当时有效的历史版本

输入：

```text
entity = GB/T 17650.2
year = 2020
type = TYPE_B
status = ADOPTED
```

候选版本：

| GB 版本               | 生效日期   | 失效日期   | 国际标准             |
| --------------------- | ---------- | ---------- | -------------------- |
| `GB/T 17650.2-1998` | 1999-10-01 | 2021-11-01 | `IEC 60754-2:1991` |
| `GB/T 17650.2-2021` | 2021-11-01 | 空白       | `IEC 60754-2:2019` |

判断：

```text
截止日 = 2020-12-31
1998 版：已实施，尚未失效 → 保留
2021 版：尚未实施 → 排除
```

结果：

```text
选择 GB/T 17650.2-1998
国际标准 = IEC 60754-2:1991
status = ADOPTED
output = 1
```

### 示例 2：明确写出的版本晚于年报年份

输入：

```text
entity = GB/T 17650.2-2021
year = 2020
status = ADOPTED
```

判断：

```text
企业明确写 2021 版
2021 版晚于 2020 年报
→ 拒绝匹配
→ 不退回 1998 版
→ output = 0
```

### 示例 3：精确版本不存在，不允许找“最接近版本”

输入：

```text
entity = GB/T 19001-2020
year = 2020
```

数据库只有：

```text
GB/T 19001-2016
GB/T 19001-2024
```

结果：

```text
没有 2020 版
→ 不用 2016 版
→ 不用 2024 版
→ 未找到映射
→ output = 0
```

### 示例 4：版本年份不晚，但实际生效日期较晚

输入：

```text
entity = 某 GB-2012
year = 2012
```

数据库：

```text
该版本生效日期 = 2013-05-01
```

判断：

```text
版本名虽然带 2012
但 2012-12-31 时尚未实施
→ 拒绝匹配
```

### 示例 5：GB 版本选对了，但没有国际标准编号

仓库测试中有类似情形：

```text
entity = GB/T 13471
year = 2020
```

历史版本选择得到：

```text
GB/T 13471-2008
```

但该测试记录中的国际标准编号为空，因此：

```text
GB 版本匹配成功
→ 国际标准编号为空
→ output = 0
```

这说明“找到 GB 版本”和“找到国际标准”是两件事。

### 示例 6：同一标准在更晚年份可以选择新版本

同样以仓库测试数据为例：

```text
GB/T 13471-2025
生效日期 = 2026-05-01
```

- 对 2020 年报：不能选择 2025 版；
- 对 2026 年报：截至 2026-12-31 已经实施，可以参与选择。

所以同一个基础编号会因年报年份不同得到不同版本。

### 示例 7：格式不同，但可以规范化为同一个标准

以下输入：

```text
gb/t 19001—2016
ＧＢ／Ｔ １９００１－２０１６
GB/T19001:2016
```

都会被理解为：

```text
基础编号 = GB/T19001
版本年份 = 2016
```

然后进入同一套精确版本匹配规则。

### 示例 8：企业明确引用已经失效的旧版本

输入：

```text
entity = GB/T 17650.2-1998
year = 2022
status = ADOPTED
```

数据库显示：

```text
该版本失效日期 = 2021-11-01
```

当前程序行为：

```text
因为企业写明了 1998 版
→ 精确找到 1998 版
→ 当前代码不检查明确版本是否已经失效
→ 仍可能映射为 IEC 60754-2:1991
→ 仍可能 output = 1
```

人工复核结论：

```text
不得自动换成 2021 版；
必须标记“明确引用已失效旧版本”，交由研究口径决定。
```

## 14. “缺失年份”要分三种情况理解

### 14.1 GB 标准没有版本年份，但年报年份存在

例如：

```text
entity = GB/T 17650.2
year = 2020
```

这是正常情况，可以按 2020-12-31 选择历史有效版本。

### 14.2 GB 标准没有版本年份，年报年份也缺失

例如：

```text
entity = GB/T 17650.2
year = 空白
```

当前代码会直接选择该基础编号中版本年份最大的候选记录，也就是倾向于选择最新版本。

这对历史年报可能产生时间错配。

因此人工操作中应遵守：

```text
标准未写版本年份 + 年报年份缺失
→ 不应直接接受最新版本
→ 先补全年报年份
→ 无法补全时进入人工复核
```

注意：当前正式输出字段中没有自动生成 `mapping_uncertain`，所以这种记录需要额外建立复核标记。

### 14.3 GB 标准写明了版本年份，但年报年份缺失

例如：

```text
entity = GB/T 17650.2-2021
year = 空白
```

当前代码会先做精确版本匹配，但因为没有年报年份，无法继续判断：

- 该版本是否晚于年报年份；
- 该版本到年报年末是否已经实施。

因此它可能直接接受精确版本。人工复核时仍应先补全年报年份；无法补全时，应标记时间判断不完整。

## 15. 时间数据不完整时怎么处理

### 15.1 `LEGACY_ONLY_NO_TEMPORAL_METADATA`

表示记录来自旧版映射表，保留了采标信息，但缺少可靠生效和失效时间。

对于没有写 GB 版本年份的实体，程序会排除这类记录，不用它自动推断历史版本。

### 15.2 生效日期缺失，但没有被标为上述旧表记录

当前代码仍可能把这类候选保留下来，并用“版本年份的 1 月 1 日”作为排序时的替代基准。

这并不等于真实生效日期就是 1 月 1 日。更重要的是：当前代码只有在 `生效日期` 存在时，才继续检查 `失效日期` 和“废止”状态。因此，生效日期缺失的候选可能绕过部分有效期检查。

人工复核时应将其理解为：

```text
程序为了排序使用的技术性替代值，不是可靠的历史事实；
该版本的历史有效性仍未被完整证明。
```

如果这类记录决定了最终版本，应增加“生效日期缺失、时间有效性不完整”的复核备注。

### 15.3 已废止但失效日期缺失

对于未写版本年份的实体，若记录具有生效日期，并且：

```text
当前状态 = 废止
失效日期 = 空白
```

程序会排除，不参与自动历史推断。若生效日期也为空，则应按照第 15.2 节进入人工复核，不能把程序保留该候选理解为“历史有效性已经确认”。

## 16. 当前输出表能看到什么、看不到什么

GB 映射完成后，当前程序在原有字段基础上增加：

| 输出字段     | 含义                                               |
| ------------ | -------------------------------------------------- |
| `国际标准` | 最终映射出的 ISO、IEC 等国际标准编号；失败时为空   |
| `采标情况` | 数据库中的采标类型；失败时通常为“未找到采标信息” |
| `output`   | 是否形成有效采用记录，取 0 或 1                    |

当前程序**不会单独输出**：

- 实际选中的完整 GB 版本；
- 匹配失败的具体原因；
- 是否属于时间不确定；
- 是否明确引用了已失效旧版。

因此，进行人工复核或方法说明时，建议另外保存这些字段：

| 建议新增的复核字段      | 示例                                                     |
| ----------------------- | -------------------------------------------------------- |
| `normalized_base`     | `GB/T17650.2`                                          |
| `entity_version_year` | 为空或`2021`                                           |
| `report_cutoff`       | `2020-12-31`                                           |
| `selected_gb_version` | `GB/T 17650.2-1998`                                    |
| `mapping_reason`      | 1998 版在截止日已生效且未失效                            |
| `review_flag`         | `explicit_expired_version`、`missing_report_year` 等 |

## 17. 人工复核时可直接照着做的操作步骤

### 第 1 步：确认是 TYPE_B

```text
type = TYPE_B？
```

不是则停止 GB 映射。

### 第 2 步：检查 entity 中是否只有一个标准号

删除：

- 标准中文名称；
- 括号中的解释；
- 认证描述；
- 同一字段中的第二个标准号。

### 第 3 步：整理标准号

记录：

```text
基础编号
版本年份（如有）
```

### 第 4 步：记录年报年份和截止日

```text
2020 年报 → 2020-12-31
```

### 第 5 步：在 GB_dict.csv 中筛选基础编号

查看该基础编号的全部版本。

### 第 6 步：根据有没有版本年份走不同分支

#### 写明版本年份

- 只查精确年份；
- 不存在则失败；
- 晚于年报年份则失败；
- 生效日期晚于年报年末则失败；
- 如年报时点已经失效，标记人工复核，不得自动换版本。

#### 未写版本年份

- 排除未来版本；
- 排除尚未实施版本；
- 排除已经失效版本；
- 排除废止但无可靠失效日期的版本；
- 排除 `LEGACY_ONLY_NO_TEMPORAL_METADATA`；
- 在剩余候选中选生效日期最晚的一版。

### 第 7 步：读取同一行的国际标准编号

国际标准为空则不能形成映射。

### 第 8 步：结合 status 判断 output

```text
映射成功 + status=ADOPTED → output=1
其他情况 → output=0
```

### 第 9 步：记录原因，而不只记录 0 或 1

尤其要区分：

- `exact_version_not_found`
- `version_after_report_year`
- `not_effective_at_cutoff`
- `no_historical_candidate`
- `missing_international_standard`
- `status_not_adopted`
- `explicit_expired_version`
- `missing_report_year`
- `temporal_metadata_incomplete`

## 18. 一页式判断流程

```text
开始
  │
  ├─ type 不是 TYPE_B
  │    └─ 不做 GB 映射
  │
  └─ type = TYPE_B
       │
       ├─ entity 格式能否整理为一个 GB 标准号？
       │    ├─ 否 → 人工修正或匹配失败
       │    └─ 是
       │
       ├─ 标准号是否写明版本年份？
       │
       ├─ 是
       │    ├─ 数据库是否存在同基础编号、同版本年份？
       │    │    ├─ 否 → 不回退，匹配失败
       │    │    └─ 是
       │    ├─ 版本是否晚于年报年份？
       │    │    └─ 是 → 匹配失败
       │    ├─ 生效日期是否晚于年报年末？
       │    │    └─ 是 → 匹配失败
       │    └─ 读取该精确版本的国际标准
       │         └─ 若该版当时已失效 → 当前程序仍可能接受，人工标记
       │
       └─ 否
            ├─ 年报年份是否存在？
            │    ├─ 否 → 当前程序会偏向最新版本；人工必须复核
            │    └─ 是
            ├─ 列出同基础编号的全部版本
            ├─ 排除未来、未实施、已失效和时间数据不可靠的版本
            ├─ 选择截止日前最近生效的一版
            └─ 读取该版本同一行的国际标准

最后：
国际标准存在且 status=ADOPTED → output=1
否则 → output=0
```

## 19. 最容易犯的十个错误

1. **直接选数据库中最新的 GB 版本。**历史年报必须选择当时有效的版本。
2. **企业写明版本，但数据库没有时自动回退。**明确版本只做精确匹配。
3. **只看版本年份，不看实际生效日期。**“2012 版”可能 2013 年才实施。
4. **直接选最新 ISO 或 IEC。**国际标准必须来自选中 GB 版本的同一行。
5. **把年报年份、GB 版本年份和 ISO 年份混为一谈。**
6. **把两个标准放在同一条 entity 中一起查。**必须拆分成两条记录。
7. **保留标准中文名称或括号说明。**可能导致标准号无法解析。
8. **认为 output=0 就等于企业没有采用。**也可能是映射失败或数据缺失。
9. **标准无版本、年报年份缺失时直接接受最新候选。**这是当前程序边界，不是可靠的历史匹配原则。
10. **企业明确写了已失效旧版时，擅自替换为新版。**
    应保留原始版本并单独标记，而不是更改企业原文含义。

---

## 20. 最后只记住六句话

1. **先清理标准号，一条记录只保留一个 GB 标准。**
2. **写明版本年份时，只做精确匹配，绝不自动换版本。**
3. **没有版本年份时，按年报年末选择当时有效的历史版本。**
4. **先选正确 GB 版本，再读取该行对应的国际标准。**
5. **映射成功且 `status=ADOPTED`，`output` 才等于 1。**
6. **年份或时间数据不可靠时，应标记人工复核，而不是凭感觉选最新版本。**
